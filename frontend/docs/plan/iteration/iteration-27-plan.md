# Iteration 27 계획 — 주문 동기화: 게이트웨이 타임아웃(504) 처리 + 누락된 수정 재반영

> 작성일: 2026-09-09

## 배경

Iteration 26(PR #227)에서 타임아웃/실패 메시지 구분, SKIPPED("이미 실행 중") 안내, 폴링 기반 버튼 잠금을 추가했다. 그런데 **PR #227이 머지된 시각(2026-09-09 11:32 KST)이 후속 커밋 2건(SKIPPED 처리 11:46, 폴링 잠금 11:54)을 푸시한 시각보다 빨라서**, 그 두 수정은 `develop`/운영에 반영되지 못한 채 브랜치에만 남아 있었다.

그 상태로 운영 배포된 버전을 사용자가 테스트한 결과, 1분 만에 "주문 동기화 실행에 실패했어요."가 떴다. 원인 조사 결과 백엔드 앞단이 **AWS ALB**이고, ALB 기본 idle timeout(60초)이 프론트의 300초 타임아웃보다 먼저 연결을 끊어 **504 Gateway Timeout**을 반환하기 때문이었다. 504는 axios의 자체 타임아웃(`ECONNABORTED`)이 아니라 정상 수신된 에러 응답이라, 기존 `isTimeout` 판별에 걸리지 않고 실패로 분류됐다.

## 범위

1. 누락됐던 두 수정을 다시 반영: SKIPPED("이미 실행 중") 안내, 폴링 기반 버튼 잠금
2. **신규**: `shouldWaitForBackend` 판별을 axios 자체 타임아웃(`ECONNABORTED`)뿐 아니라 게이트웨이 타임아웃(HTTP 502/503/504)까지 포함하도록 확장 — ALB/프록시가 먼저 끊어도 "실패"가 아니라 "계속 실행 중일 수 있음"으로 처리하고 폴링

## 범위 제외 (인프라, 이 저장소 밖)

- ALB idle timeout을 300초 이상으로 늘리는 것은 AWS 콘솔에서 별도로 처리 필요 — 이 저장소에는 인프라 코드(Terraform 등)가 없어 여기서 처리 불가
