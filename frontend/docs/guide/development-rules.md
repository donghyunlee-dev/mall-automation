# 🧭 React Frontend Development Rules

## 🎯 목적

이 문서는 Claude Code가 React Frontend 프로젝트를 구현할 때 따라야 하는 공통 개발 기준을 정의한다.  
목표는 다음과 같다.

- 요청 범위 내에서만 변경한다.
- 동작하는 코드를 우선한다.
- 빌드·린트 검증이 가능한 구조를 유지한다.
- 유지보수성과 확장성을 해치지 않는 설계를 선택한다.
- React 18 + TypeScript strict 기반의 일관된 품질 기준을 적용한다.

---

## 📌 적용 범위

이 문서는 다음 범위의 작업에 적용한다.

- 신규 컴포넌트 또는 페이지 구현
- 기존 컴포넌트 수정
- 버그 수정
- API 연동 추가 또는 변경
- 커스텀 훅 추가 또는 수정
- 스타일(CSS Modules) 추가 또는 수정

다음 작업에는 추가 확인이 필요하다.

- 라우팅 구조 변경
- 빌드 도구 또는 설정 파일 변경
- 의존성 추가 또는 버전 업그레이드
- 전역 스타일 또는 디자인 토큰 변경
- 배포 설정 변경

---

## 🏗️ 기본 설계 원칙

### 단일 책임 원칙

- 컴포넌트는 UI 렌더링에만 집중한다.
- 비즈니스 로직은 반드시 커스텀 훅으로 분리한다.
- API 호출은 `src/api/` 함수를 통해서만 한다.

### 단순성을 우선한다

- 가장 단순한 해결책을 먼저 선택한다.
- 추상화는 필요가 생겼을 때만 도입한다.
- 미래 가능성만으로 구조를 과도하게 일반화하지 않는다.

### 중복을 제거한다

- 유사한 UI 패턴, 훅 로직은 공통화 가능성을 먼저 검토한다.
- 단, 너무 이른 공통화로 책임이 섞이지 않도록 주의한다.

---

## 🧱 아키텍처 원칙

### 계층 구조

- **Pages**: 라우팅 단위 컴포넌트, 훅과 컴포넌트를 조합
- **Components**: UI 단위, Props로 데이터를 받고 렌더링만 수행
- **Hooks**: 비즈니스 로직, 상태 관리, API 호출 조율
- **API**: 외부 통신 전담, Axios 인스턴스(`client.ts`)만 사용
- **Types**: Props, API 요청/응답 타입 정의

### 의존 방향

- Pages → Components
- Pages / Components → Hooks
- Hooks → API
- API → client.ts (Axios 인스턴스)

다음 구조는 금지한다.

- 컴포넌트에서 `axios` 또는 `client` 직접 호출
- 컴포넌트에 비즈니스 로직 작성
- 훅에서 `axios` 직접 import
- `any` 타입 사용

### 폴더 구조

```text
src/
├── api/
│   ├── client.ts        ← Axios 인스턴스, 인터셉터
│   ├── auth.ts
│   ├── goods.ts
│   └── batch.ts
├── components/
│   ├── layout/
│   ├── dashboard/
│   └── modals/
├── pages/
├── hooks/
├── types/
├── styles/
│   ├── _variables.scss
│   ├── _reset.scss
│   └── global.scss
└── utils/
```

---

## 🔌 API 분리 원칙

- 모든 API 호출은 `src/api/` 함수로 캡슐화한다.
- `client.ts` 인터셉터가 401 오류를 `/login`으로 리다이렉트한다 (단, `/api/auth/` 경로 제외).
- API 응답 타입은 완전히 정의한다. `any`는 금지한다.
- 외부 응답 타입과 내부 타입은 분리한다.

---

## 🧪 빌드 및 린트 우선 원칙

구현 완료 후 반드시 다음을 검증한다.

- `npm run build` — TypeScript 오류 없이 완료
- `npm run lint` — 린트 오류 없이 통과

실패 시 구현이 완료되지 않은 것으로 간주한다.

---

## 🎨 스타일 규칙

- 컴포넌트 스타일은 CSS Modules(`.module.scss`)만 사용한다.
- 인라인 스타일은 금지한다. 동적 값은 CSS 변수로 처리한다.
- 전역 디자인 토큰은 `_variables.scss`에서만 정의한다.
- UI 구현은 `docs/design/mockup.html`과 `docs/design/mockup-login.html`을 기준으로 한다.
- CSS 변수명과 클래스명은 목업 기준을 따른다.

---

## 🌐 컴포넌트 설계 규칙

### 컴포넌트

- 함수형 컴포넌트만 사용한다.
- Props 타입은 파일 상단 `interface`로 정의한다.
- `any` 타입 사용을 금지한다.
- 렌더링 로직만 포함한다. 상태 관리는 훅으로 분리한다.

### 훅

- 단일 관심사에 집중한다.
- 이름은 `use`로 시작한다.
- 비동기 처리, 에러 상태를 명시적으로 반환한다.

### 타입

- `src/types/`에 도메인 단위로 정의한다.
- Props 타입은 각 컴포넌트 파일 내 선언한다.
- 모든 API 요청·응답 타입을 명시한다.

---

## 🧹 코드 스타일 규칙

### 네이밍

| 대상 | 규칙 | 예시 |
|---|---|---|
| 컴포넌트 파일 | PascalCase | `ProductTable.tsx` |
| 훅 / 유틸 / API | camelCase | `useGoods.ts`, `client.ts` |
| 스타일 모듈 | 컴포넌트명 동일 | `ProductTable.module.scss` |
| 타입 / 인터페이스 | PascalCase | `GoodsItem`, `BatchStatus` |
| 상수 | UPPER_SNAKE_CASE | `PAGE_SIZE` |

### 조건문과 흐름 제어

- 중첩보다 early return을 우선한다.
- 컬렉션은 null 대신 빈 배열을 우선한다.
- `undefined` 체크는 명시적으로 한다.

### 주석

- 코드가 설명하지 못하는 의도를 보완할 때만 주석을 사용한다.
- 구현 내용을 반복 설명하는 주석은 피한다.

---

## 🧾 오류 처리 규칙

- API 오류가 사용자에게 명확히 반영되거나 명시적으로 처리된다.
- 오류를 silent fallback으로 숨기지 않는다.
- 발생할 수 없는 케이스에 대한 오류 처리를 추가하지 않는다.
- 유효성 검사는 시스템 경계(사용자 입력, API 응답)에서만 수행한다.

---

## 🔐 보안 규칙

- 토큰, 인증 정보 등 민감한 값을 소스 코드에 하드코딩하지 않는다.
- 설정값은 환경 변수(`.env`, `.env.production`)로 관리한다.
- 인증 흐름(`withCredentials: true`, 세션 쿠키)을 정상 동작하도록 유지한다.
- 사용자 입력은 시스템 경계에서 검증한다.

---

## ⚙️ 설정과 환경 규칙

- 환경별 차이는 `.env` 파일로 해결한다.
- `vite.config.ts`, `tsconfig.json` 등 설정 파일 변경 시 추가 확인이 필요하다.
- TypeScript strict 모드를 유지한다.

---

## 🩺 디버깅 규칙

- 디버깅 시 원인과 해결 가설을 먼저 정리한다.
- 원인 불명 상태에서 무작정 수정하지 않는다.
- 재현 조건을 먼저 확보한다.
- 에러 제거보다 정상 동작 보장을 목표로 한다.

---

## 🛠️ 리팩토링 규칙

- 리팩토링은 구조 개선이 목적이며 기능 변경이 아니어야 한다.
- 사용자 승인 없이 대규모 리팩토링을 진행하지 않는다.
- 리팩토링 전후 빌드와 린트가 모두 통과해야 한다.
- 범위를 벗어난 리네이밍, 파일 이동은 금지한다.

---

## ✅ 구현 완료 체크리스트

다음 항목을 만족해야 구현 완료로 본다.

- 요구사항 범위 내에서만 변경했다.
- 컴포넌트, 훅, API 책임이 분리되었다.
- 비즈니스 로직이 컴포넌트에 없다.
- 모든 API 호출이 `src/api/`를 통한다.
- `any` 타입이 사용되지 않는다.
- 인라인 스타일이 없다.
- UI가 목업과 일치한다.
- `npm run build`가 오류 없이 통과한다.
- `npm run lint`가 오류 없이 통과한다.
- 변경 파일 수와 수정 범위가 최소화되었다.

- 어떤 명령으로 검증했는지
- 빌드·린트 결과가 어떠한지
- 추가 개선점이 있다면 현재 범위 밖의 항목으로 분리했는지

## 📊 다이어그램 작성 규칙 (Mermaid)

문서에서 구조·프로세스·관계도는 ASCII 아트가 아닌 **Mermaid 코드 블록**(` ```mermaid `)으로 작성한다.

- 의도에 맞는 유형을 선택한다.
  - 프로세스·데이터 흐름 → `flowchart`
  - 행위자/시스템 간 호출 순서 → `sequenceDiagram`
  - 데이터 모델 관계(ERD) → `erDiagram`
  - 상태 전이 → `stateDiagram-v2`
- 다이어그램 하나에는 하나의 관심사만 담는다. 복잡해지면 분리한다.
- 노드 라벨은 한국어 허용, 길면 `<br/>`로 줄바꿈한다.
- UI 와이어프레임·목업, 폴더 트리는 Mermaid가 부적합하므로 텍스트 블록을 유지한다.
- 다이어그램 라벨·예시 값에 개인정보(PII)·시크릿을 넣지 않는다.

## 🚫 금지 사항

- 요청 범위를 벗어난 기능 추가
- 관련 없는 코드 리팩토링
- 컴포넌트에 비즈니스 로직 작성
- 컴포넌트 또는 훅에서 `axios` 직접 호출
- `any` 타입 사용
- 인라인 스타일 사용
- 확인되지 않은 추측성 수정
- 사용자 승인 없는 대규모 구조 변경
- 명시적 요청 없는 의존성 추가 및 버전 업그레이드
