# WMS 로그인 연동 가이드

## 목적

이 문서는 로그인 화면에서 시작해 WMS 로그인 API를 호출하고, 로그인 결과로 받은 세션 쿠키를 이후 WMS 요청에 어떻게 사용하는지 설명한다.

## 전체 흐름

연동은 다음 순서로 진행한다.

1. 로그인 화면에서 사용자 입력을 받는다.
2. 원문 비밀번호를 받은 경우 Java의 SHA-256 해시로 변환한다.
3. WMS 로그인 API를 호출한다.
4. 응답에서 세션 쿠키를 추출한다.
5. 세션 쿠키를 메모리에 보관한다.
6. 이후 WMS에 보내는 다른 요청에 같은 세션 쿠키를 포함한다.

세션 쿠키는 로그인 결과값이며, 같은 실행 흐름 안에서 바로 사용해야 한다.

## 로그인 화면에서 받아야 하는 값

로그인 화면은 최소한 다음 값을 받아야 한다.

| 이름 | 타입 | 설명 |
|---|---|---|
| `loginUrl` | string | WMS 로그인 URL |
| `userId` | string | WMS 사용자 ID |
| `password` | string | 사용자가 입력한 비밀번호 |

## 비밀번호 처리 규칙

- 사용자가 원문 비밀번호를 입력하면, 먼저 SHA-256 해시로 변환한다.
- 이미 해시된 값을 받는 구조라면 다시 해시하지 않는다.
- WMS 요청에 넣기 전에 필요한 경우 URL 인코딩을 적용한다.

## 로그인 API 명세

### 요청 방식

- `GET`

### 요청 URL

- `loginUrl`

### 쿼리 파라미터

| 파라미터 | 필수 | 값 |
|---|---:|---|
| `CURRENT_MENUCODE` | 예 | `LOGIN` |
| `SELLANGBEFORELOGIN` | 예 | `KO` |
| `USERID` | 예 | `userId` |
| `LOGIN_USERID` | 예 | `userId` |
| `PASSWORD` | 예 | SHA-256 해시된 비밀번호 |

### 요청 예시

```text
GET {loginUrl}?CURRENT_MENUCODE=LOGIN&SELLANGBEFORELOGIN=KO&USERID={userId}&LOGIN_USERID={userId}&PASSWORD={encodedPassword}
```

### 성공 결과

- 응답 헤더에 `Set-Cookie`가 포함된다.
- 첫 번째로 파싱 가능한 쿠키를 세션 쿠키로 사용한다.

### 실패 결과

- `Set-Cookie` 없음
- 쿠키 파싱 실패
- 통신 실패

실패한 경우에는 로그인 완료로 처리하지 않고, 세션이 필요한 다음 API 요청도 진행하지 않는다.

## 세션 사용 순서

정확한 순서는 다음과 같다.

1. 로그인 화면에서 사용자 입력을 받는다.
2. 원문 비밀번호라면 SHA-256 해시로 변환한다.
3. 로그인 API를 호출한다.
4. 응답의 `Set-Cookie`에서 세션 쿠키를 추출한다.
5. 세션 쿠키를 메모리에만 보관한다.
6. 같은 세션 쿠키를 이후 WMS API 요청에 포함한다.
7. 세션이 만료되거나 거부되면 로그인부터 다시 시작한다.

세션 쿠키는 장기 저장용 토큰이 아니라 실행 중 임시 세션 값으로만 사용한다.

## 결과값

### 로그인 결과

- 세션 쿠키 객체
- 쿠키를 추출하지 못하면 로그인 실패로 판단한다.

## API 사용 규칙

- 로그인 성공 전에는 세션이 필요한 WMS API를 호출하지 않는다.
- 로그인 화면에서는 인증 실패 메시지를 사용자에게 보여주고, 세션을 저장하지 않는다.
- 성공 후에는 세션 쿠키를 포함한 요청만 보내야 한다.
- 세션 쿠키는 검증 없이 재사용하지 않는다.

## 보완 설명

- 이 문서는 로그인 화면과 로그인 API 사용법에만 적용한다.
- 이후 WMS의 다른 기능은 별도 문서로 분리한다.
